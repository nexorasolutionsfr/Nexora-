## 2. Architecture retenue, appliquée à UN chemin

La base garde documents, autorisations, files et états. Le dashboard prépare,
fait relire, autorise, affiche. n8n **réserve** ce qui est autorisé et
**transporte** ; il ne recalcule aucune règle, ne résout aucun garage, ne
compose aucun message.

Le chemin représentatif : **la relance d'un travail différé**
(`20260919000400_relances_travaux_differes.sql`).

```
candidat        travaux_differes échu (statut planifie / a_relancer, date_relance ≤ aujourd'hui)
brouillon       preparer_relances_travaux()      → relances_travaux.a_relire   [service_role]
autorisation    autoriser_envoi_relance_travail() → en_attente                 [dirigeant / accueil]
réservation     reserver_relances_travaux()      → envoi_en_cours (SKIP LOCKED) [service_role]
tentative       n8n : SMTP (prod) / Code simulé (test)
résultat        terminer_relance_travail()       → envoye | bloque | a_reprendre (→ en_attente, tentatives < 3)
```

Contrat d'une ligne : `garage_id` (identité du garage), `travail_differe_id`
+ `echeance` (identité d'idempotence — une relance par travail et par
échéance ; un report crée une autre échéance, donc une autre relance
possible, jamais un doublon accidentel), `statut`, `motif` /
`derniere_erreur`, `destinataire_valide`, `empreinte_document`,
`autorise_par`, `tentatives`.

Conditions **relues à la réservation** : travail encore ouvert, échéance
inchangée, destinataire inchangé, message inchangé. Ce qui a bougé est mis de
côté (`bloque`) avec le motif, et **revalidé à la main**.

`envoi_en_cours` n'est jamais recyclé par un délai. Un timeout après une
acceptation possible du fournisseur reste incertain ; l'écran dit « Envoi à
vérifier ». Pas de promesse « exactement une fois » avec SMTP.

**Une seule composition** : `composer_relance_travail()` en base, au moment de
la préparation. L'aperçu de l'écran et l'e-mail sont le même texte. C'est la
réponse au constat des « deux composeurs » de « véhicule prêt ».

### Réveil événementiel : non testé, et pourquoi

Les webhooks de base Supabase peuvent réveiller un consommateur, mais ils ne
font pas une file durable, et le Mac hôte endormi ne reçoit rien. Le workflow
livré est une **relève périodique bornée** (`*/15`), qui retrouve ce qui a été
manqué. Aucun tunnel public n'a été ouvert. Le réveil événementiel est
documenté comme **non testé**.

### Mesure

Sur Test, le chemin a été joué par script (`relances-travaux-serveur.mjs`),
pas par n8n : 32 contrôles, dont la concurrence de réservation et le blocage
après modification. **Nombre d'exécutions n8n utiles/vides : non mesuré**, le
workflow n'ayant pas tourné. À `*/15`, une tournée fait 96 exécutions/jour par
workflow, la plupart vides ; c'est le coût à mesurer sur une fenêtre connue
avant toute extrapolation.

## 4. IMAP, avis Google : conditions, pas d'interrupteur

- **IMAP** : pas de garage de secours, pas de routage sur l'expéditeur libre.
  L'identité de la boîte/connecteur autorisé doit déterminer le garage ; un
  transfert partagé ne prouve rien. Messages et pièces jointes = entrées non
  fiables, jamais des instructions. Activation après connecteur authentifié
  **par garage** et recette de livraison réelle. **Rien de livré cette nuit.**
- **Avis Google** : lien d'avis propre au garage (`garages.lien_avis_google`
  existe), retrait persistant (n'existe pas), règle d'éligibilité, aucune
  sélection des seuls satisfaits, aucune récompense. **Non commencé** ; la
  branche reste indisponible (`CAPACITES.demandeAvis.disponible = false`).

### Vraie variante contre un SMTP contrôlé (15 sept. 2026)

`recette-smtp.json` = les nœuds de `production.json` (vérifié : mêmes nœuds,
plus le déclencheur manuel), sur Test, borné à un garage neuf, identifiant SMTP
visant `scripts/recette/smtp-controle.mjs` (127.0.0.1, n'accepte que
`@nexora-recette.invalid`, ne relaie rien). Deux passages :

| Cas | Passage 1 | Passage 2 |
|---|---|---|
| accepté (250 après le message) | `envoye` | non repris, rien renvoyé |
| 451 au RCPT TO | `en_attente`, tentatives 1 | repris, tentatives 2 |
| 550 au RCPT TO | `bloque` | non repris |
| message reçu puis connexion coupée | `envoi_en_cours` (incertain, rien clos) | **non repris** |

n8n ne transmet au nœud d'échec que le **texte** de l'erreur
(`{ error: "Connection closed unexpectedly" }`, sans code SMTP structuré) :
`classerEchec.js` ne lit donc que les formulations de nodemailer **ancrées en
début de message** (« all recipients were rejected: 451 », « Message failed:
554 »…), jamais un nombre trouvé ailleurs ; tout le reste est incertain
(8 tests unitaires).

## 6. Fiche de chaque automatisation concernée

**Relance de travail différé** (implémentée et testée, non publiée, activation bloquée)
- *Déclencheur* : relève `*/15` ; aucun envoi à l'échéance seule.
- *Autorisation* : le garage relit et autorise chaque message
  (`autoriser_envoi_relance_travail`, dirigeant ou accueil) ; refusée si le
  client est opposé ; relue à la réservation (travail ouvert, échéance,
  destinataire, texte, opposition).
- *Destinataire* : l'e-mail du client figé à l'autorisation ; changé depuis →
  mis de côté.
- *Expéditeur* : `"<nom du garage>" <nexorasolutions.france@gmail.com>` (identité
  Brevo vérifiée, même que le socle), Reply-To = e-mail du garage s'il est valide.
- *Doublons* : une relance par (travail, échéance) ; réservation atomique
  `SKIP LOCKED` ; `envoi_en_cours` jamais repris.
- *Erreurs* : refus certain avant ou après le message → `a_reprendre` (4xx,
  3 tentatives) ou `bloque` (5xx) ; coupure, délai, inconnu → incertain, reste
  `envoi_en_cours`, écran « envoi à vérifier ».
- *Manques qui bloquent l'activation* : aucun écran pour enregistrer une
  opposition (la fonction `revenue_recovery_enregistrer_permission` existe,
  réservée au propriétaire) ; aucun moyen de s'opposer dans le message ; base
  légale à confirmer ; pas d'activation par garage (Production = tous les
  garages) ; réception réelle via Brevo non prouvée.

**Nouveau devis (socle)** (publié, actif)
- *Déclencheur* : cron `*/2`. *Autorisation* : `autoriser_envoi_devis`, refusée
  si chiffrage incomplet ; **l'empreinte signe désormais le contenu lu par le
  client** (001000) : libellé, constat ou photo modifiés → mis de côté,
  revalidation. *Destinataire* : figé. *Expéditeur* : même identité.
  *Doublons* : réservation atomique. *Erreurs* : selon le workflow publié
  (non modifié par ce lot).

**Dépendance au Mac** : l'instance n8n vive (`nexora-n8n`) tourne dans Docker
sur le Mac de Baptiste. Mac éteint ou endormi : aucun envoi du socle, aucune
relance ; au réveil, la relève reprend ce qui est autorisé (rien ne part deux
fois, des messages peuvent partir en retard). La pile hébergée
(`infra/n8n-heberge/`) est préparée, **non migrée** ; aucun changement cette nuit.

## 8. Sauvegarde, restauration, exécutions

Instance vive : SQLite dans le conteneur, sauvegarde par `n8n export:workflow
--all --backup` (dernier export complet : `Desktop/Nexora - Automatisation/
Workflows n8n/export-complet-2026-09-11/`) et copie du volume. Pile cible
(`infra/n8n-heberge/`) : Postgres + `sauvegarder.sh` / `restaurer.sh`,
répétition complète le 10 sept. La conservation des exécutions se règle par
`EXECUTIONS_DATA_PRUNE` / `EXECUTIONS_DATA_MAX_AGE`
(https://docs.n8n.io/hosting/scaling/execution-data/) — **aucune purge n'a
été faite sur la base vive**. Le sondage à 2 minutes produit ≈2 900
exécutions/jour pour le socle ; cela établit un volume, **pas** une cause de
corruption SQLite : aucune affirmation causale n'est retenue.
